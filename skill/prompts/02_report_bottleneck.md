# 提示词模板 02 · 从综合报告定位性能瓶颈

## 适用场景

HLS 综合（csynth）跑完了，实测吞吐远低于预期，但报告上**没有任何报错**，
主循环 II 也显示 1。需要找出真正的瓶颈。

## 在本项目中的效果

这是本项目最有价值的一次定位。现象：op 1~11 全部 20.57 ms（6.70 cyc/px），
而 csynth 报 II=1、无任何警告。

用这套提示词排查后定位到：**条件 DDR 写导致 HLS 推不出 AXI burst**——
写操作写在 `if (x >= 2)` 里，地址不连续、且有条件，burst 推断失败，
退化成"每像素一次带握手的独立传输"。改成无条件连续写后
20.57 ms → 3.258 ms（**6.31×**）。

## 提示词模板

```
我的 HLS 核实测吞吐远低于预期，但综合报告没有报错。信息如下：

【实测：X ms / 帧，图像 WxH，时钟 F MHz，算下来 Y cyc/px】
【预期：接近 1 cyc/px（II=1 的理论地板是 N ms）】
【csynth 报告摘要：主循环 II = ?，是否有警告】
【核心循环代码（贴出来）】

请按下面的顺序排查，**每一步都要给出"怎么验证"**：

1. 先算清楚理论地板：像素数 / 时钟频率 = ? ms。
   实测是地板的几倍？这个倍数本身就指明了方向：
   - 接近 1 倍 → 已经到访存上限，别再优化计算
   - 2~4 倍 → 大概率是流水化问题（II 没到 1 或有气泡）
   - >5 倍 → 大概率是**访存模式**问题（burst 没推断出来、每次传太少）

2. 检查 AXI burst：csynth 报告的 "M_AXI Burst Information" 里，
   每个端口是 Inferred 还是 Fail？
   **写出会导致 burst 推断失败的几种写法**（条件写、地址不连续、
   循环内多次访问同一端口等），逐一对照我的代码。

3. **找反例**：如果这个瓶颈成立，哪些现象会**推翻**它？
   （例：若真是 burst 问题，那么"无条件写的那个算子"应该明显更快——
    我们当时正是靠 op 0 GRAY（无条件写）3.222 ms 这一条判据锁定的）

4. 只有通过了第 3 步，才给修改方案。方案要说明代价（资源、边界行为）。
```

## 使用说明

- **第 1 步的倍数判断最省力**。它能直接把排查范围从"整个设计"缩到"一类问题"。
- **第 3 步是这套模板的灵魂**。我们有过一次归因失败：
  怀疑"σ 单累加器"是瓶颈，改了两天无效——因为没先找反例。
  后来发现：走另一条通路、**完全没有 σ 累加**的算子一样慢，
  一条判据就推翻了原假设。见 `../cases/02_performance_method.md`。

## 失效条件

- 若实测已接近理论地板（1 cyc/px 左右），说明瓶颈在**访存带宽**而非代码写法，
  再优化 HLS 代码收益为零，该去改数据通路（位宽、数据布局）。
- burst 推断在 AXI3（Zynq-7000）上限 16 beat，写更大的值只会被拆分，不解决问题。
